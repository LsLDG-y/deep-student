## 本项目采用的评测单位

本版使用 **34 个独立提交结果的任务包**，每题给出用户可观察的症状和预期行为，要求候选定位原因、提交修复，并保留相关正常行为。既测“为什么这里有缺陷”的工程理解，也测把修复落实到项目真实接口的能力。它不是无提示、开放式全库安全审计：有题面线索的诊断结果不能单独代表发现任意未知缺陷的能力。

借鉴 SWE-bench 的补丁交付单位和 Harbor 的任务/验证分离，但不为此引入整套外部调度框架。当前任务数、单仓库与已有工具链可以由本套运行器承担；只有实际出现新的环境或调度需求，才有理由增加框架依赖。[S1][S5]

SWE-bench Pro 面向长时工程任务。本项目有意收窄为代码阅读可能较广、参考修复主要为小中改动的 Debug/Coding 切片；不把“多改文件”当作高难度的替代指标，也不把整轮笔记架构升级包装成一题。任务量通过选题边界和统一预算控制，而不是按 Agent 调用次数、关键词或相似度中止工作。[S3][S4]

### `historical_backport` 与原始历史 checkout 的区别

| 方面 | 原始历史 checkout 任务 | 本版 `historical_backport` |
|---|---|---|
| 起点 | 每题恢复该 issue 的历史 base commit | 所有题使用同一个项目锚点，再移植有历史 diff 证据的旧缺陷行为 |
| 工程环境 | 每题可能需要不同依赖、构建和接口 | 统一依赖、接口与运行基线，降低历史环境漂移对分数的干扰 |
| 历史保真 | 更接近当时开发者面对的整个代码状态 | 保真目标是本题可观察缺陷与修复契约，不是整仓逐字复原 |
| 副作用 | 可能同时包含当时大量无关缺陷 | 保留锚点后续无关修复，隔离本题目标 |
| 结果解释 | 针对历史 issue 环境的解题能力 | 针对当前工程环境中真实历史缺陷行为的诊断/修复能力 |

SWE-bench Pro V2 的任务镜像仍位于各自 base commit，虽然清理了可泄漏答案的历史。本项目不是照搬该做法：统一锚点是明确的成本与可比性选择，应在结果中保留 `historical_backport` 标记，不能宣称完全复现了当年的整段开发经历。[S4]

## F2P + P2P 与严格解题率

借鉴 SWE-bench 的两组行为判据：[S2]

- **FAIL_TO_PASS（F2P）**：在缺陷变体失败、参考变体通过，代表必须修复的行为。
- **PASS_TO_PASS（P2P）**：在两种变体都通过，代表修复必须保留的相邻正常行为。

本项目的机器得分是**严格解题率**。一题只有在完整、预先校准的测试清单都实际执行、所有 F2P 和 P2P 都通过、运行有效且退出状态正常时才得 1；否则得 0。测试缺失、被跳过或报表不完整不能变成成功。SWE-bench 的当日实现存在针对部分历史数据/runner 的特殊兼容语义，例如 P2P skip 或 failure-only 解析；本项目不继承这些兼容分支，使用自身明确的完整测试契约。[S2]

缺省总分以发布的 **34 题为固定分母**：

```text
严格解题率 = 100 × 已严格解决题数 / 34
```

每题等权；没有提交的题记 0，不能只报已尝试题的通过率。F2P/P2P 的断言通过比例仅作诊断信息，不自动给部分分。评测基础设施异常必须单独披露，不允许通过悄悄删除失败题缩小分母；若参考对照无法运行，这轮正式比较的有效性尚未建立，应先处理环境问题。

同时报告按**难度**与**家族**拆分的结果，但这些是解释性切片，不改变缺省每题等权的总分。难度 1–4 是维护者根据阅读范围、状态机和跨层契约作出的**启发式策划标签**，尚无多模型成功率标定，不应当作客观能力分级。此处“启发式”只描述离线难度标注，不是任何限制 Agent 输出/工具调用的自动守卫。共享提交或模块的家族存在经验迁移，训练示例与保留测试应按家族拆分；不能把 34 题描述成 34 个互不相关的历史事故。

性能候选或环境特定题在正式纳入前必须完成对应平台的对照校准。若要排除候选，应在运行前发布新的固定任务子集/版本，并完整标明分母；不得在看到模型结果后再删题。

## 三个阶段与两个对照

SWE-bench Pro V2 明确将候选运行与正式 verifier 分离，再把捕获的补丁重放到 pristine image；SWE-bench-Live 明确禁止在 rollout 前/中安装 test_patch，也禁止使用 ground-truth 反馈继续优化答案。本项目据此将三个阶段分开。[S4][S6]

1. **候选阶段**：新建缺陷工程工作区，只提供题面、工程源码和正常开发工具。可以自己写复现脚本或测试，但不提供隐藏测试、测试名称清单、修复 SHA、参考补丁和逐题历史说明。每题独立一次提交过程，不能把隐藏评测变成可循环查询的训练信号。
2. **机器评测阶段**：从固定材料重新物化全新缺陷工程，只应用提交补丁，然后由维护者侧注入未改变的隐藏 verifier。候选运行后的缓存、修改过的测试、伪造报告与其他未提交状态都不是机器评测的输入。
3. **外部复核阶段**：读取机器结果、提交补丁、诊断与复现材料，检查根因解释、是否只针对测试值硬编码，以及改动范围；输出单独结论。

正式启用一题之前，至少有两个对照：[S1][S4]

- **Empty/nop control**：缺陷工程不应用候选修复，应该无法严格解决；同时必须有 P2P 证明相关正常行为可运行。
- **Gold/reference control**：参考工程或经过确认的参考修复应通过完整清单。

两个对照的意义是验证题目和 verifier，而不是额外考核候选的文字表现。对照失败时先修复题目/环境；不能降低断言要求来迁就某个模型，也不能根据模型答案动态生成判分条件。题面必须支持每项要求，隐藏的是验证输入和实现，不是未告知的产品需求。Pro V2 对模糊题面、失效测试和 gold 补丁的重新审查，正说明“来自真实提交”仍不足以自动保证题目有效。[S4]

## 隔离能防什么，不能防什么

**文件与阶段隔离**减少候选直接复制答案或篡改评测材料的机会；**fresh sandbox replay**排除在候选工作区偷偷修改测试/报表而获分；**no-network**减少查询公开修复和向外传递评测材料的通道。依赖应在准备阶段固定并安装，正式候选与 verifier 运行阶段只依赖准备好的环境。需要联网调用模型时，应由宿主控制平面承担，或只允许已声明的模型端点；这不等于开放候选 shell 的任意网络访问。Pro V2 的官方协议对 Agent 阶段和准备/verifier 阶段有不同网络策略，本项目应如实公布自己实际执行的策略，不能只引用其名称。[S4]

**拥有同机完整权限的 Agent，无法仅靠本套 Python/测试脚本防作弊。** 如果候选能读取宿主原仓库、private 目录、评测器进程或修改 Docker/系统配置，文件名约定和“请勿查看答案”的提示都不构成安全边界。正式比较必须由外部运行环境实施权限、挂载与网络隔离；本地开发模式的结果不能被宣称具有同等防作弊能力。

即使使用全新离线容器，**JavaScript 被测源码与测试通常仍在同一进程**。候选可能写出依赖测试环境、具体夹具或评测时序的行为；只读隐藏文件和日志退出码检查不能证明修复具有业务普适性。Rust/SQLite 的行为测试同样不能枚举所有输入。机器通过证明的是预先声明测试契约，不是补丁绝对不存在投机行为。

因此不增加关键词、代码片段相似度、调用次数或轮数“作弊检测器”。这些规则既容易误判正常实现，也替代不了执行权限边界。疑似 test-aware 或硬编码修复由二轮复核依据具体代码和反例判断；外部 reviewer 可以提出额外独立复现，但不能把隐藏评测反馈回流给同一次候选继续调参。[S4][S6]

## 诊断能力的二轮入口

**纯机器评分不自动给文字洞察分。** 候选的 `DIAGNOSIS.md` 与复现证据交给外部 Agent，可包含触发条件、失败现象、根因涉及的状态/数据流、修复前后观察及剩余边界。不因写得长、出现正确术语、引用了某个文件或碰巧与参考修复措辞相同而加分；也不要求采用与参考补丁逐字一致的实现。

外部复核读取的材料包括机器结果与日志、候选补丁、`DIAGNOSIS.md`、复现输入和输出、必要的参考行为材料。输出符合 `review-response.schema.json`：

- `reviewer_id`、`task_id` 标明谁在复核哪一题；不把该字符串当作认证凭据。
- `root_cause_valid`、`non_hardcoded_fix`、`scope_appropriate` 分别说明根因是否成立、是否为一般化修复、范围是否适当；证据不足用 `null`。
- `verdict` 为 `accept`、`reject` 或 `needs_review`，配合 `reasoning` 和可定位的 `evidence[]`。

这个响应**不包含覆盖机器分的字段，也不自动改变机器分**。复核通过、拒绝或待查应与原始机器得分并列保留；任何组织层面的最终采信决定是显式的外部流程。当前只定义接口，不实现第二轮 reviewer 或自动仲裁。
