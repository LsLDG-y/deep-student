## 从提交记录到可计分任务

筛选不是按标题中有没有 `fix` 或“高难”决定。先用日志找候选，再查看实际 diff、前版本及后续使用路径，分离可独立重现的旧行为；只选能以现有生产函数/模块和稳定夹具执行的切片。保留小、中改动，不要求整个历史大提交可回滚。每题将旧行为回移到统一锚点，避免 3 个月依赖、接口、构建链变化成为额外混杂因素。

机器可验证的结论是：“在本次声明环境与输入下，缺陷变体失败、参考变体通过，且指定既有行为保持通过。”它不证明历史上此前的每次尝试都失败、不证明某个提交是世界范围最后一次修复，也不证明整个原生应用在全部场景没有问题。正式校准报告和测试边界见 `CATALOG.zh-CN.md`。

## 有实际 diff 支持的补修链

本版尚未建立“同一根因至少三次代码修复失败、最后一次成功”的完整逐次复现链，因此没有给任何任务贴上该标签。下列补修证据不自动升级为这种更强结论；例如压缩提交记录的多次运行失败，描述的是操作尝试，不是多次独立代码修复。

### 设置批量保存：最清晰的同一契约补修（D02）

- **2026-09-05，`88a48fb67`**：给批量写入增加已写键回滚。原实现先用宽松 `getSettings` 读旧值，随后逆序补偿。

恰当结论是“第一版回滚有效覆盖正常补偿，但遗漏了故障组合，后来补齐”，不能说第一次实现完全无效。

## 防历史答案泄漏的处理

候选工作区不应带原仓库 `.git`、维护者目录、隐藏测试、历史审阅文档、AGENTS 中的修复记忆或答案补丁。仅把 Git 历史藏起来还不够：部分生产源码注释直接叙述“某天修复了哪个错误、应改为哪种算法”。领域任务 D01/D02/D04/D08/D11/D12 在 `case.json.redactions` 中列出精确文本替换，将这些修复叙事换成中性的 API 说明；固定和缺陷物化快照均应用同一 redaction。只处理注释，未修改生产仓库及运行代码。

正常业务接口名、已有可复用函数和公开类型仍应保留。找到工程现有实现并复用正是 Coding/Debug 能力的一部分，不能为了制造难度把整个工程人为剪碎。注释脱敏不能防住能访问原仓库或互联网答案的候选：正式运行仍需独立工作目录、无宿主源码挂载、隐藏评测材料与受控网络。完整隔离/计分入口以运行器说明为准。
